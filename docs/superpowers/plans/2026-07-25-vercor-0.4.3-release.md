# VerCOR 0.4.3 Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prepare, merge, tag, publish, and verify VerCOR 0.4.3 through the
documented release path.

**Architecture:** Keep `pyproject.toml` as the only executable VerCOR version
owner, update the active release contracts and documentation around it, and
preserve the already-committed generic GitHub workflow. Verify one immutable
release commit locally and in pull-request CI, tag the exact protected-main
merge commit, and let the tag-only workflow publish the checksum-bound
artifacts.

**Tech Stack:** Python 3.13 in the `scipy` Conda environment, pytest, Black,
flake8, mypy, Flit/build, Twine, Git, GitHub Actions, GitHub CLI, the GitHub
connector, and PyPI.

## Global Constraints

- The release version is exactly `0.4.3`; the annotated tag is exactly
  `v0.4.3`.
- Work on `release/vercor-0.4.3` in
  `.worktrees/release-vercor-0.4.3`.
- `pyproject.toml` remains the sole executable VerCOR version owner.
- Do not hard-code 0.4.3 into `.github/workflows/python-package.yml`.
- Preserve `v0.4.0`, `v0.4.1`, and `v0.4.2` exactly; never delete, overwrite,
  or repoint them.
- Preserve historical release evidence and the compatibility floor
  `vercor>=0.4.0,<0.5`.
- The only release artifacts are `vercor-0.4.3-py3-none-any.whl` and
  `vercor-0.4.3.tar.gz`.
- The tag-triggered GitHub workflow is the only authorized publisher.
- Do not manually upload to PyPI or mutate a partial GitHub Release without
  separate explicit recovery approval.
- No commit may contain failing tests.
