# VerCOR 0.4.0a1 Protocol-First API Design

## Historical implementation status

This document preserves the approved design intent. Its compatibility adapter
was planned but not delivered: Task 9 was explicitly skipped, and no legacy
compatibility namespace was implemented. References to that adapter
below describe the original plan rather than shipped `0.4.0a1` behavior.

## Goal

VerCOR 0.4 replaces the overlapping legacy public extension paths with one
structural component contract, one-shot coupler assembly, explicit workflow
planning, chunk-oriented execution backends, unified output providers, stable
exchange route identities, and private immutable preparation bindings.

The release is intentionally breaking. The original design proposed opt-in
adapters for legacy applications; the primary 0.4 modules do not retain legacy
aliases.

## Public architecture

The package root exports exactly `Clock`, `Coupler`, `Exchange`,
`RectilinearGrid`, `RunState`, and `RuntimeOptions`. Advanced contracts have a
single canonical owner module.

`vercor.components.Component` is a structural `Protocol` with `name`, `grid`,
`spec`, and `step`. `CallableComponent` and `DataComponent` are the only
concrete convenience adapters. `ComponentSpec` exclusively owns inputs,
outputs, initial fields, execution capability, lifecycle hooks, transfer
policy, and output policy. A single setup hook returns `SetupResult(fields,
payload)`; there is no component `initialize`, `initial_fields`, constructor
payload, or separate payload-creation hook.

`Settings` is replaced by a frozen JAX-PyTree `PhysicalConstants`. Precision is
owned only by `RuntimeOptions.dtype`; setup-specific configuration is a frozen
dataclass owned by the setup or external plugin.

`Coupler` is configured completely by its constructor. `CouplerSpec`, the
`vercor.coupling` facade, and public mutators are removed. Configuration objects
are treated as immutable after construction; callers build a new coupler to
change configuration.

## Execution and output

`Workflow.build(WorkflowContext) -> ExecutionPlan` returns exactly one
ascending `StepPlan` for every clock step. Plans may reorder or omit registered
components, but may not reference unknown names or call one component twice in
the same clock step. Fractional-time subcycling is out of scope.

The private coordinator splits the plan at output boundaries. An
`ExecutionBackend` executes each `ExecutionChunk` and advances it only through
`RuntimeDriver.run_step`. The core retains validation, output cadence,
accumulation, cancellation, and finalization. Incoming driver states and every
returned chunk state are checked for exact component/field/mask names, grid
coordinates, shapes, dtypes, and finite mask ranges.

An `OutputProvider` returns an `OutputFrame` with variables, coordinates,
dimensions, and metadata. One coordinator owns selection, cadence, immutable
mean accumulation, host transfer, paths, NetCDF writes, final fields, and
snapshots for generic, JAXGCM, Veros, CAMulator, and third-party providers.
`Coupler.run(output=None)` performs no I/O; `OutputTarget` explicitly enables
it.

## Coupling contracts

Every `Exchange` has a stable route ID. The default is
`"{source}->{target}"`; collisions require an explicit ID. Topology patches use
route IDs rather than callable-derived tuple keys. Scalar `Regridder` and
`VectorRegridder` capabilities are separate and validated against route fields.
Ambiguous target-field fan-in remains an error.

`RunState` is opaque. Only `component`, `components`, and immutable
`replace_fields` are public; alignment and mask storage stay private.

## Compatibility and release

The proposed legacy compatibility namespace adapts valid legacy component
classes/structural objects, settings, coupler recipes/mutators, runtime
options/backends, exchanges,
topology patches, and post-run output. Using the namespace warns. It remains
supported through 0.4.x and is removed no earlier than 0.5.0. Expired APIs are
not restored.

The first implementation release is `0.4.0a1`. Explicit dependency injection
remains the plugin mechanism. Registries, entry-point discovery, Pydantic,
fan-in reducers, public prepared graphs, and subcycling are deferred.
