# VerCOR 0.4 API Hardening Design

## Goal

Harden the existing protocol-first VerCOR 0.4 API without replacing its
assembly model or introducing a registry. The work fixes evidenced correctness
and compatibility gaps while preserving the current component, exchange,
workflow, backend, topology, state, and output extension points.

The stable extension tier remains deliberately small: root assembly
conveniences and the canonical contracts in `vercor.components`,
`vercor.coupler`, `vercor.exchanges`, `vercor.grids`, `vercor.state`,
`vercor.runtime`, `vercor.regridding`, `vercor.topology`, `vercor.output`, and
`vercor.physics`. Existing numerical, setup, diagnostics, and logging exports
remain available during the alpha, but their implementation-oriented methods
are not promoted into the semantic plugin compatibility tier.

## Chosen approach

Use focused stability hardening rather than a contract-only documentation pass
or a broad internal reorganization.

- A contract-only pass would leave evolving external-model state outside
  `RunState`, so supplied or reused states could produce non-reproducible runs.
- A broad reorganization of runtime schemas and output coordination would add
  substantial regression risk without being necessary to close the public API
  gaps.
- Focused hardening fixes the demonstrated state-ownership, component-identity,
  plugin-installation, typing, and documentation problems while retaining the
  current architecture.

No registry, entry-point discovery, Pydantic configuration hierarchy, public
prepared graph, fan-in reducer, or new inheritance hierarchy is added.

## Component identity and lifecycle

`Component` remains a structural protocol with `name`, `grid`, `spec`, and
`step`. The `name`, `grid`, and `spec` attributes form the static component
identity captured by `Coupler` construction. Lifecycle callbacks may prepare
resources and runtime payloads, but they may not replace or mutate that static
identity.

Private preparation records the declared identity and validates it again after
setup. A changed name, grid, or specification raises `ComponentError` with the
component name and changed attribute before an initial state is returned. This
keeps `Coupler.components` useful as the original author-object view without
allowing its visible assembly identity to diverge from the prepared runtime.

The implementation should compare the canonical declaration rather than
perform broad reflection over arbitrary author attributes. Model-owned caches
that do not change `name`, `grid`, or `spec` remain outside this check, although
evolving simulation state must follow the payload rule below.

## External-model state ownership

All component/model state that changes during a run belongs to `RunState`.
Veros and CAMulator adapters therefore place their initial native model state,
cursor/index state, and output-relevant evolving values in
`SetupResult.payload`. Run-scoped output accumulators and interrupt state remain
owned by their existing private coordinators rather than by a component.

Each host step follows this flow:

```text
RunState payload
      |
      v
adapter step(native state, fields, StepContext)
      |
      v
StepResult(fields=..., payload=replacement native state)
      |
      v
replacement RunState
```

Closures retain only immutable model definitions, configuration, compiled
functions, and other static resources. A step must not advance closure-owned
state. Output providers and snapshot writers read `OutputContext.payload` or
`SnapshotContext.payload`, so emitted data always corresponds to the supplied
runtime state rather than to the most recently mutated adapter closure.

This design must preserve the existing host execution capability. Opaque host
payloads may change structure as already permitted by the runtime; JAX-backed
payloads retain the existing PyTree schema requirements.

## Time alignment and logging

CAMulator validates calendar support and forcing alignment during lifecycle
setup, before execution. `CAMulatorConfig.time_alignment` is the explicit
policy and accepts only `"strict"` or `"forcing_start"`; the default is
`"strict"`. Strict alignment requires the coupler and CAMulator forcing starts
to match. `"forcing_start"` explicitly requests the existing CAMulator-start
indexing behavior. The implicit warning-and-reindex path is removed. The
hardening must not invent generalized calendar conversion.

`Coupler` remains the owner of runtime logging. External setup code receives
the lifecycle context logger. If a model must log before lifecycle setup, its
bootstrap logger is typed as `LoggerLike`; untyped `Any` logger configuration
is removed or narrowed. Model-specific configuration must not create a second
runtime logging policy.

## Plugin and typing contracts

The public plugin fixture declares `vercor>=0.4.0a1,<0.5`, which includes the
package version under test. Installed-plugin checks use ordinary dependency
resolution rather than relying exclusively on `--no-deps`. A non-default
plugin configuration exercises every configuration field, including forcing,
initial temperature, and step count, without a backend overwriting the value
before it is observed.

`RegridderFactory` is one unconditional runtime-checkable `Protocol`. Static
type checkers and runtime introspection therefore see the same callable
signature. The implementation does not use a `TYPE_CHECKING`-only alias.

Compatibility tests distinguish semantic public behavior from Python/JAX
implementation hooks. Public PyTree hooks such as `tree_flatten` remain
available where required by JAX, but are not treated as independent user
workflow commitments. Existing public modules are not removed in this
hardening release.

## Documentation and examples

The architecture review will retain its eight required sections and add an
explicit priority/decision record for the remaining findings. It will identify
the stable extension tier and the provisional alpha helper surface without
claiming that private layout or JAX protocol hooks are stable user APIs.

An executable plugin-author guide will demonstrate:

1. a plugin-owned frozen configuration and factory;
2. a structural JAX or host component;
3. an injected regridder and topology policy;
4. a custom workflow and backend;
5. output from runtime payload state; and
6. a small fake component for isolated tests.

The existing custom-component example gains behavioral test coverage. The
incorrect `vercor.vector()` documentation reference becomes
`vercor.fields.vector()`. `DESIGN.md`, `DEPENDENCIES.md`, migration material,
and `PROGRESS.md` are updated only where implementation changes their durable
contracts or dependency order.

## Errors and compatibility

The hardening release intentionally changes these invalid or ambiguous cases:

- lifecycle mutation of component identity raises `ComponentError`;
- unsupported CAMulator time alignment fails during setup;
- external adapters no longer preserve hidden evolving state between runs; and
- plugin dependency metadata explicitly accepts the 0.4 alpha.

Valid 0.4 constructor, component, exchange, custom workflow/backend, topology,
state replacement, and output workflows remain unchanged. No legacy
compatibility namespace is introduced. The package remains an alpha, so provisional helper
contracts may evolve, while the public plugin fixture protects the documented
extension tier.

## Test-first implementation

Implementation is split into independently verifiable changes. Every behavior
change starts with a failing regression test.

1. Add component-identity mutation failures, then validate the canonical
   declaration after lifecycle setup.
2. Add repeated/supplied-state reproducibility tests for Veros and CAMulator,
   then move evolving native state and output sampling to payloads.
3. Add CAMulator setup-time alignment failures, then implement explicit
   validation.
4. Add static/runtime `RegridderFactory` contract tests, then unify the
   protocol definition.
5. Add normal dependency-resolution and non-default installed-plugin tests,
   then fix plugin metadata and smoke behavior.
6. Add executable plugin-author and custom-component documentation tests, then
   update the documents and examples.

Focused tests run after each change. Final verification includes Black, strict
flake8, mypy, compileall, `git diff --check`, the fast and full pytest suites,
branch coverage, package builds, and installed VerCOR/plugin artifact smokes.

## Deferred cleanup

The audit also found duplicated runtime-schema views and split output
coordination. They remain private and are deferred because the focused fixes do
not require reorganizing them. A later internal-only change may introduce one
runtime schema owner or merge output finalization, provided it does not expand
the public API or alter plugin behavior.
