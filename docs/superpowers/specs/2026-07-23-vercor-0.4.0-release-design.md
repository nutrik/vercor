# VerCOR 0.4.0 Release Design

## Objective

Prepare the current `refactor` branch for a stable VerCOR `0.4.0` release
without publishing, tagging, pushing, creating a hosted release, or broadening
the release into unrelated redesign work.

## Assessment

VerCOR is a Python 3.12+ package built with Flit from `pyproject.toml`. The
project uses pytest with xdist, Black, Flake8, mypy, coverage.py, and GitHub
Actions. `pyproject.toml` is the authoritative version declaration; the
package reports installed versions through distribution metadata rather than a
source `__version__`.

The preceding documented stable baseline is the superseded baseline tag, and
the current candidate is `0.4.0a1`. The current branch has no local tags. GitHub
connector access is not installed for the `nutrik/verec` owner, so hosted releases, remote tags, and
checks cannot be verified through the connector. The local fast baseline passes
664 tests on Python 3.13.13 with four identical third-party Flax/JAX
deprecation warnings.

Stable-release metadata is duplicated intentionally in release-contract tests,
the public-signature manifest name, active documentation, CI artifact paths,
release commands, and the public-plugin fixture. Historical alpha records in
the changelog, progress archives, and prior Superpowers records remain
historical evidence and must not be rewritten.

## Chosen Approach

Use focused release hardening:

1. Change release-contract tests first so they describe stable `0.4.0`
   metadata and artifact names.
2. Make the smallest corresponding metadata, documentation, CI, contract, and
   fixture changes.
3. Run focused validation after each release-contract group.
4. Run every locally available release gate, build artifacts once, install and
   smoke-test those exact artifacts, and record evidence.
5. Fix only confirmed release-critical failures. Record unrelated or
   environment-specific findings as limitations.

A metadata-only bump is rejected because it would leave Alpha classifiers,
artifact paths, tests, and user documentation inconsistent. Broad refactoring
is rejected because the current functional baseline is clean and unrelated
changes would increase release risk.

## Release Changes

### Version and maturity

- Change `project.version` in `pyproject.toml` from `0.4.0a1` to `0.4.0`.
- Replace `Development Status :: 3 - Alpha` with
  `Development Status :: 5 - Production/Stable`.
- Keep Python support at 3.12 and 3.13 as currently documented and tested by
  CI.
- Do not add a second source version declaration.

### Public compatibility evidence

- Rename the current public-signature contract to
  `tests/contracts/vercor-0.4.0-public-signatures.json`.
- Update executable API and distribution contracts to require the stable
  version, classifier, contract filename, artifact filenames, and plugin
  dependency floor.
- Preserve the six-symbol package root and documented stable extension tier.
- Do not change runtime behavior unless validation exposes a concrete
  release-critical defect.

### Documentation and release metadata

- Add a dated `0.4.0` changelog entry based only on repository history after
  `0.4.0a1` and work completed during this release task.
- Preserve the `0.4.0a1` changelog entry and comparison link as historical
  records.
- Update active README, design, architecture review, migration, plugin
  authoring, dependency-order, release-procedure, and CI references from the
  alpha candidate to stable `0.4.0` where they describe current state.
- Change the public plugin fixture dependency to `vercor>=0.4.0,<0.5`.
- Add concise hosted-release notes at `docs/release-notes-0.4.0.md`, including
  upgrade guidance, compatibility implications, and known limitations.
- Keep historical alpha evidence in `PROGRESS.md`, progress archives, earlier
  specifications, and earlier plans. Add a new current release-verification
  entry rather than rewriting old evidence.

### CI and artifacts

- Update GitHub Actions paths to the stable wheel and source-distribution
  filenames.
- Update release commands to build, inspect, hash, install, and smoke-test
  `vercor-0.4.0-py3-none-any.whl` and `vercor-0.4.0.tar.gz`.
- Build the VerCOR wheel, VerCOR source distribution, and public-plugin wheel
  once from the final local source state.
- Inspect archive contents and metadata, verify PEP 561 markers, reject cache
  and platform files, install wheel and source distribution separately, and
  run the existing installed-artifact boundary.

## Validation

Run the repository's supported local gates with the `scipy` Conda environment:

- Black check over `vercor`, `examples`, and `tests`.
- Flake8 over the repository with the documented 120-character limit.
- mypy over `vercor`, `examples`, and `tests`.
- compileall over `vercor`, `examples`, and `tests`.
- focused release-contract tests.
- fast pytest suite.
- full pytest suite.
- branch-coverage suite with the 90% floor.
- optional JCM/Veros release nodes.
- output-free JVP and reverse-mode gradient nodes.
- distribution build and installed-artifact boundary.
- strict public-plugin smoke/type-check through the artifact boundary.
- `git diff --check`.
- tracked/untracked release-marker and accidental-file inspection.
- SHA-256 hashes for final distributions.

The local environment provides Python 3.13.13. Python 3.12 execution and hosted
GitHub Actions status can only be claimed if they are actually run and observed;
otherwise the final report will identify those as maintainer/CI checks.

## Error Handling

If a focused or full gate fails:

1. Reproduce the failure with the smallest relevant test.
2. Determine whether it predates the release changes.
3. Add or update a regression test before production-code changes when
   practical.
4. Apply the smallest robust fix.
5. Re-run the focused test and the affected broader gate.

Warnings will not be suppressed merely to obtain a clean report. Third-party
warnings that cannot be fixed safely in VerCOR will be recorded with their
source and count.

## Release Boundary

The repository will be left ready for maintainer review. This task does not
authorize a commit, tag, push, force push, upload, package publication, hosted
release, or merge. The final report will provide the suggested commit message
`Release 0.4.0`, intended tag `v0.4.0`, tag annotation, publication commands,
post-publication verification, and recovery guidance.
