# VerCOR 0.4.6 Release Design

**Date:** 2026-08-27

**Status:** Approved design; specification pending user review

## Purpose

Prepare the complete VerCOR 0.4.6 release candidate on
`release/vercor-0.4.6` and open a ready-for-review pull request against
`main`. The candidate packages every change merged after `v0.4.5`, removes
all tracked references to VerCOR release series older than 0.4, and verifies
the complete source, documentation, tests, and built distributions.

This work does not create or move a tag, publish a package, upload release
artifacts, merge the pull request, or create a GitHub Release.

## Release contents

VerCOR 0.4.6 packages the following completed work from `main`:

1. A capability-gated differentiable JAX execution lane for the Veros fork,
   including stable multi-step forward- and reverse-mode differentiation.
2. CI provenance, dependency-installation, isolation, and combined-coverage
   checks for stock and differentiable Veros execution.
3. `VerosConfig.execution` as the sole Veros execution-policy option, with the
   redundant and misleading `jitted` option removed.
4. Complete copy ownership of stock-Veros state, preserving diagnostics and
   future native additions without enumerating attributes.
5. Correct JCM sigma-level height evaluation and validation of hybrid-sigma
   height calculations.
6. Repository-wide removal of VerCOR release references older than the 0.4
   series, including historical archives, migration records, tests, and
   generated release guidance.

The release preserves the stable 0.4 public API. It does not add a public
symbol, compatibility adapter, registry, output mode, or unrelated runtime
refactor.

## Legacy-reference boundary

The cleanup applies to every tracked text file and tracked path in the release
tree. A forbidden reference is an explicit VerCOR-owned version label, series
shorthand, tag, artifact, API name, fixture name, migration name, or path for a
release series older than 0.4. The rule also covers case variants and labels
assembled in source solely to evade the repository scanner.

The cleanup will:

- delete the obsolete version-to-version migration page;
- remove that page from Sphinx navigation, README links, dependency inventory,
  and executable documentation tests;
- rewrite active architecture, compatibility, changelog, release-note, and
  release-runbook prose so it describes the supported 0.4 line without naming
  earlier VerCOR release series;
- redact or rewrite pre-0.4 VerCOR labels in archived progress, historical
  Superpowers specifications, and historical implementation plans while
  preserving useful design and verification context; and
- replace old-version negative examples in tests with generated semantic cases
  that do not leave forbidden literal labels or paths in the tracked tree.

The boundary does not reject unrelated scientific numbers or versions owned by
external dependencies, actions, schemas, or fixture distributions. For
example, an independently versioned test plugin may retain its own `0.1.0`
package identity. Existing Git history and immutable remote tags are outside
the tracked-tree cleanup and will not be rewritten, deleted, or moved.

## Enforcement design

`tests/test_versioning_policy.py` remains the executable repository-wide
owner. Its tests will first be strengthened so the current tree fails for the
newly forbidden references. The scanner will distinguish VerCOR-owned labels
from external and numeric contexts, inspect tracked filenames as well as file
contents, and report concise path-and-line diagnostics.

The policy must not rely on a fixed enumeration of a few historical patch
labels. It must classify any semantic VerCOR version below `0.4.0`, including
an optional `v` prefix and prerelease or patch suffix, when the adjacent text or
tracked path establishes VerCOR ownership. Test cases may construct candidate
labels from integer components so the enforcement test does not itself retain
the forbidden literal text it rejects.

After the policy is red for the expected repository references, production
documentation and tests will be changed until the complete tracked-tree scan
is green. Assertions dedicated only to the deleted migration page will be
removed; still-useful executable examples will remain covered through the
README, researcher, developer, and plugin-authoring documentation tests.

## Release metadata and documentation

`pyproject.toml` remains the sole executable VerCOR version owner and changes
from `0.4.5` to `0.4.6`. No source `__version__` is introduced.

The maintained release surface will be synchronized to 0.4.6:

- `CHANGELOG.md` gains a dated `0.4.6` section covering the release contents,
  changes the Unreleased comparison base to `v0.4.6`, and adds the
  `v0.4.5...v0.4.6` comparison link.
- `docs/release-notes-0.4.6.md` provides concise highlights, upgrade commands,
  compatibility guidance, and current optional-model limitations.
- `README.md` and `docs/researchers/getting-started.rst` identify 0.4.6 as the
  current stable installation target.
- `docs/project-resources.rst` publishes the 0.4.6 release notes and omits the
  deleted migration page.
- `docs/releasing.md` uses the exact 0.4.6 branch, version, tag, artifact,
  release-title, notes-file, PyPI, and recovery identities throughout its
  executable fail-closed transcript.
- `PROGRESS.md` records the red-green cycle, quality gates, test counts,
  coverage, artifact names, sizes, checksums, installed-artifact smoke results,
  review outcome, and pull-request handoff.

`DESIGN.md`, `DEPENDENCIES.md`, `docs/api-architecture-review.md`, archived
progress files, and historical Superpowers records change only as needed to
remove forbidden release references or to record an actual inconsistency found
during verification.

## Source and test audit

The complete `vercor/` and `tests/` trees will be included in release
verification. The audit checks public manifests and signatures, frozen PyTree
and dtype contracts, optional-model lazy imports, JAX transformations, host and
compiled execution, exchange/regridding behavior, output boundaries, setup
gallery behavior, command-line installation, and distribution contents.

No runtime change is planned beyond the work already merged on `main`. If the
audit exposes a source defect, implementation stops at the first failing
boundary, adds a focused regression, and fixes the owning source. Numerical
failures are traced to their equation or data boundary; no fudge factor,
warning suppression, skip, weakened assertion, or unrelated refactor is
allowed.

## Test design

Implementation follows red-green-refactor:

1. Strengthen the repository policy and documentation/release contracts so
   they fail for the current legacy references and 0.4.5 metadata.
2. Run the focused tests and retain concise evidence that failures match the
   intended missing 0.4.6 state.
3. Remove or rewrite forbidden references, delete the obsolete migration page,
   and update release metadata and documentation with the smallest changes
   satisfying the contracts.
4. Run focused tests after each coherent cleanup group and refactor only after
   they are green.

The final candidate must pass:

- focused versioning-policy, documentation, architecture, release-state,
  distribution, Veros, JCM, runtime, and gradient tests;
- Black formatting, strict flake8, mypy, compileall, workflow YAML parsing,
  embedded release-transcript Bash syntax, warning-as-error Sphinx, and
  whitespace checks;
- the configured fast suite, complete suite, and branch-coverage suite at the
  existing 90 percent minimum;
- a fresh build containing exactly `vercor-0.4.6-py3-none-any.whl` and
  `vercor-0.4.6.tar.gz`;
- Twine validation and repository distribution-boundary tests; and
- isolated installed-wheel and installed-source-distribution smoke tests for
  metadata version, the six-symbol root API, and the installed `vercor`
  command.

Known third-party warnings may remain only when they match the existing
documented Flax/JAX warning set. A new warning or failing gate is a release
blocker.

## Failure handling

Release-state operations remain fail-closed. Implementation stops if it finds
an existing conflicting 0.4.6 tag, published package, release branch, or pull
request. The GitHub preflight performed during design found no existing
`release/vercor-0.4.6` branch or corresponding pull request; the branch created
for this approved work started from `3d2f713`.

Every material discovered defect is documented in `PROGRESS.md`, including
failed approaches. Existing user changes are never discarded or overwritten.
The source checkout was clean before branch creation, and the isolated branch
baseline passed 807 fast tests with four known third-party Flax/JAX warnings.

## Git and pull-request handoff

Work proceeds in the isolated worktree `.worktrees/release-vercor-0.4.6` on
`release/vercor-0.4.6`. Changes are committed in small, testable units: the
approved design and plan, policy/tests, tracked-tree cleanup, release metadata
and documentation, any regression-backed audit correction, and final evidence
where practical.

After fresh final verification and review, the branch is pushed to `origin`.
The selected GitHub integration opens a ready-for-review pull request against
`main`. The PR body lists the release contents, exact verification evidence,
artifact identities, known third-party warnings, the scope of the legacy
reference purge, and the explicit statement that no tag, publication, artifact
upload, merge, or GitHub Release was created.

## Non-goals

- Do not tag `v0.4.6`.
- Do not merge the release pull request.
- Do not publish to PyPI or upload wheel or source-distribution artifacts.
- Do not create or modify a GitHub Release.
- Do not rewrite Git history or delete or move historical tags.
- Do not change the public 0.4 API or add unrelated refactors.
- Do not remove versions owned by external dependencies or fixture packages.
