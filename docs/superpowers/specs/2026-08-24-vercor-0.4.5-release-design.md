# VerCOR 0.4.5 Release Design

**Date:** 2026-08-24

**Status:** Approved for implementation

## Purpose

Prepare the complete VerCOR 0.4.5 release candidate on
`release/vercor-0.4.5` and open a ready-for-review pull request against
`main`. The candidate includes every change merged after `v0.4.4` plus the
approved JAXGCM runtime logging cleanup. This work does not create a tag,
publish a package, upload an artifact, or create a GitHub Release.

## Release contents

VerCOR 0.4.5 packages the following completed work from `main`:

1. Dinosaur 1.3.6 and JCM 2.0.1 dependency updates and the corresponding JCM
   adapter migration.
2. Correct preservation of complete land and sea temperatures on fractional
   JCM surface cells, including finite forward- and reverse-mode gradients.
3. The transform-safe no-NaN numerical policy across preparation, exchange,
   regridding, component execution, transfer, and bundled native payload
   boundaries.
4. Setup-gallery runtime corrections for target-domain masks, conservative
   ocean-mask cutoffs, JAX x64 initialization, portable NetCDF boolean
   encoding, and CAMulator composition coverage.
5. Removal of unsolicited per-step JAXGCM surface-temperature information
   messages and the computations used only by those messages.

The release preserves the stable 0.4 public API. It does not add a new public
symbol, compatibility alias, registry, output mode, or configuration option.

## Runtime change

`vercor/setups/_external/jax_gcm_runtime.py` currently emits two model-specific
information messages during ordinary execution:

- the mean sea-surface temperature for each component step; and
- the number of cells below the cold-surface threshold for each host record.

These messages duplicate data available through component fields and output
providers, add noise to long coupled integrations, and perform reductions that
are unrelated to stepping the model. The existing working-tree edit removes
the logger calls. Implementation will complete that change by also removing
the now-unused logger binding and cold-cell cleanup calculation.

The change must not alter `StepResult`, `JAXGCMRuntimePayload`, applied forcing,
host-side native state mirrors, output sampling, JIT behavior, or derivatives.
A regression test will exercise the real callback boundary with a recording
logger and prove that the removed messages are absent while state recording
still occurs.

## Release metadata and documentation

`pyproject.toml` remains the sole executable VerCOR version owner and changes
from `0.4.4` to `0.4.5`. No source `__version__` is introduced.

The maintained release surface will be synchronized to 0.4.5:

- `CHANGELOG.md` gains a dated `0.4.5` section covering the five release
  contents above, changes the Unreleased comparison base to `v0.4.5`, and adds
  the `v0.4.4...v0.4.5` comparison link.
- `docs/release-notes-0.4.5.md` provides concise highlights, upgrade commands,
  compatibility guidance, and current optional-model limitations.
- `README.md` and `docs/researchers/getting-started.rst` identify 0.4.5 as the
  current stable installation target.
- `docs/project-resources.rst` publishes the maintained 0.4.5 release notes
  alongside the retained 0.4.3 and 0.4.4 records.
- `docs/releasing.md` uses the exact 0.4.5 branch, version, tag, artifact,
  release-title, notes-file, PyPI, and recovery identities throughout its
  executable fail-closed transcript.
- `PROGRESS.md` records the TDD cycle, quality gates, test counts, coverage,
  artifact names, sizes, checksums, installed-wheel smoke, review result, and
  PR handoff once those results exist.

`DESIGN.md` already describes the runtime and numerical contracts shipped by
this candidate. `DEPENDENCIES.md` already records the JCM 2 dependency graph.
They will change only if verification exposes an actual architectural or
dependency inconsistency.

## Test design

Implementation follows red-green-refactor:

1. Add a focused JAXGCM logging regression that fails against the original
   logger calls for the expected reason.
2. Update version, README, documentation-inventory, release-note, runbook, and
   artifact-identity contracts so they fail while the repository still names
   0.4.4.
3. Make the smallest runtime, metadata, and documentation changes that satisfy
   those contracts.
4. Refactor only after focused tests are green.

The final candidate must pass:

- focused JAXGCM, versioning, documentation, architecture, distribution, and
  release-state tests;
- Black formatting, strict flake8, mypy, compileall, workflow YAML parsing,
  embedded release-transcript Bash syntax, warning-as-error Sphinx, and
  whitespace checks;
- the configured fast suite, full suite, and branch-coverage suite;
- a fresh build containing exactly `vercor-0.4.5-py3-none-any.whl` and
  `vercor-0.4.5.tar.gz`;
- Twine validation and the repository distribution-boundary tests; and
- an isolated installed-wheel smoke for metadata version, the six-symbol root
  API, and the installed `vercor` command.

Known third-party warnings may remain visible only when they match the existing
documented Flax/JAX and JCM/xarray warnings. A new warning or failing gate is a
release blocker.

## Failure handling

Runtime defects found during verification receive a failing regression before
their fix. Numerical discrepancies are traced to their owning equation or
boundary; no fudge factor, warning suppression, skipped test, or weakened
assertion is permitted.

Release-state operations remain fail-closed. The implementation must stop if
it finds an existing conflicting 0.4.5 tag, published package, release branch,
or pull request. The GitHub query performed during design found no existing
0.4.5 branch or pull request.

The existing uncommitted JAXGCM edit is user-owned release input. It is
preserved, completed within the approved boundary, and never discarded or
overwritten.

## Git and pull-request handoff

Work proceeds on `release/vercor-0.4.5`, forked from commit
`b71dc01d3c9e9a5a973adf2d673b4459dacacafc`. Changes are committed in small,
testable units: the approved design, the runtime regression and cleanup, the
release metadata/documentation, and final evidence where practical.

After fresh final verification and independent review, the branch is pushed to
`origin` and a ready-for-review pull request is opened against `main`. The PR
body lists the release contents, exact verification evidence, artifact
identities, known third-party warnings, and the explicit statement that no tag,
PyPI publication, artifact upload, or GitHub Release was created.

## Non-goals

- Do not tag `v0.4.5`.
- Do not merge the release pull request.
- Do not publish or upload wheel or source-distribution artifacts.
- Do not create or modify a GitHub Release.
- Do not change the public 0.4 API or add unrelated refactors.
- Do not retain the removed JAXGCM diagnostics behind a new flag.
